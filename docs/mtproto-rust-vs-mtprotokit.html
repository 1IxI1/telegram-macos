Downloads

TelegramCore's real download path (multipartFetch, MultiplexedRequestManager) with each engine.

Why big files are faster. These changes apply only with the Rust engine:
  • The app tells the server it can use the CDN. Before, big files always came from the file's own DC.
  • The download window adapts: it starts at 6 parts, grows while parts return within 1 s, halves when a part takes over 2 s, and tops out at 16 parts (32 on the CDN). Parts grow from 128 KB to 512 KB once a file downloads faster than 4 MB/s.
  • CDN downloads may use 8 connections × 4 requests; regular DCs keep 4 × 3 so scrolling stays smooth.
  • CDN problems (bad data, endless reuploads, missing hashes, an invalid token) fall back to the file's DC without losing data already received.

Tested beyond the comparison

These run the Rust engine in-process, so they have no MtProtoKit numbers: MtProtoKit is Objective-C and has no such harness.

How it was measured

  • TelegramCore path (mtproto-bench tc, suites quick, torture-quick, hostile-quick): the real TelegramCore stack (initializedNetwork, MultiplexedRequestManager, Download, multipartFetchV2, Network.request) runs once with each engine against a fake Telegram cluster (main DC, file DC, CDN) behind a network simulator.
  • Hostile and torture suites: the fake server misbehaves on purpose, from single faults to an attacker that reacts to what the client does. It validates message times like the real server.
  • CPU and memory are for the whole client process (TelegramCore plus the engine), measured by the OS.
  • Real servers: NetworkLab in the Debug app, heavy account, read-only.
  • Rust numbers are from the final code, telegram-ios master 34d02f4dc4. The live kill-switch layer in that commit was added after these runs; an A/B against the code without it showed no measurable difference. The before column of the final pass is beta build 283245.

Not measured yet

  • A real-server big-file download (from @macos_stable_updates_files) after the fast-download change. NetworkLab has a bigfile scenario for it, but it needs the Debug app closed.
  • MtProtoKit fuzzing and soak. They would need an Objective-C harness; an hour-long run through the TelegramCore bench would work for both engines.
  • A real-server comparison with TDLib. The test account has 2FA, so TDLib was checked only without logging in. Its source was the reference for every protocol decision.
  • The iOS Bazel build. iOS keeps MtProtoKit either way.
