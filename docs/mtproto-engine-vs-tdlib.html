MTProto Engine vs tdlib

We ran tdlib's own session stack and our Rust engine against the same fake Telegram server, over the same simulated networks, call for call. Wherever tdlib lost, the cause is traced to its source below. Where it looked better, we either explained it or took the idea and improved on it.

Contenders
Rust engine r16 (mtproto-engine 6be75ca + this round)
tdlib 1.8.49 (e894536b2), CMake Release
Ground
mtproto-testserver behind mtproto-netsim on one Mac (6 performance cores), same link seed for both engines in every round
Scenarios
13 quick scenarios × 3 rounds and 48 weak-link scenarios, each in foreground (online) and background (offline) mode
Summary

What the race showed

Of 122 paired comparisons (61 scenarios, foreground and background), our engine was more than 10% ahead on some measure in 60 and tdlib in 9, four of them both ways; 57 were even. tdlib lost 242 calls in total, all on links that silently stop delivering; we lost none. Every tdlib lead is examined in section 03. One of them was a real edge (uploads over a lossy link), and we have matched it since.

What is tdlib's own code

The harness links tdlib's static libraries and runs its real Session, SessionConnection, RawConnection, obfuscated transport, fake-TLS TlsInit, AuthData, NetQuery, StateManager and FloodControlStrict. Every timeout, ping, resend and container decision in the results is tdlib's.

ConnectionCreator needs the whole Td object, so its client_loop is replicated line by line as a small actor. The replica keeps the same flood limits, the 1→16 s background backoff, the check-mode ping, up to three checking connections and the 10 s ready-connection pool, with one pool per session as in tdlib.

Foreground and background

tdlib changes its timers with the online option, which an app sets while it is in the foreground. Our engine has the same flag on its main session. Every scenario ran in both modes, because the modes behave very differently.

Paired rounds share the network seed, so both engines meet the same stalls and resets. The quick suite shows the median of 3 rounds. The weak suite shows one paired run per mode. Rows where tdlib came out ahead were rerun or explained in section 03.

Four harness differences penalized tdlib in the first passes. All four are fixed in every number on this page.

The harness started tdlib's server-time difference at 0, where tdlib starts from Clocks::system() − Time::now(), so every session's first call paid a bad_server_salt round trip. All tdlib sessions shared one thread, where real tdlib runs download and upload sessions on its slow-net scheduler. The replica marked an address faulty on every failed connect, where tdlib does so only from its connection stats, which sent it into check mode too often. And it used check mode through the fake-TLS proxy, which tdlib never does. Fixing these took tdlib's typical blackhole call from 2.6 s down to 1.4 s, removed a satellite tail, and took its flaky fake-TLS p99 from 0.99 s down to 0.66 s. Each looked like a tdlib weakness, and none of them was.

02

Proven tdlib weaknesses

Each weakness below has the numbers that show it and the lines of tdlib that cause it. Where a cause was in doubt, it was confirmed by switching it off in the harness and running again.

W1 · background

In the background, a dead connection is kept for 135 seconds

When a path dies without a reset (a NAT entry expires, Wi-Fi hands over to a captive portal, a middlebox drops the flow), no socket error ever arrives. In the background tdlib then waits for its read timeout, and every call made in the meantime waits with it.

Cause in tdlib

td/mtproto/SessionConnection.h:145–163

// td/mtproto/SessionConnection.h
double rtt() const {
  return max(2.0, raw_connection_->extra().rtt * 1.5 + 1);
}
double read_disconnect_delay() const {
  return online_flag_ ? rtt() * 3.5 : 135 + random_delay_;
}
double ping_disconnect_delay() const {
  return online_flag_ && is_main_ ? rtt() * 2.5 : 135 + random_delay_;
}

With online_flag_ false, both the read and the ping timeouts are 135 s plus jitter. SessionConnection has no transport-level check of its own, so nothing ends the wait sooner. In the outage run the 150 calls hit their deadline first.

What our engine does

An unanswered call starts a probe whose timeout follows the measured round trip: RTT + 4·RTTVAR, at least 1 s and at most 8 s. We also read the kernel's send queue, to tell a path that stopped acknowledging from one that is merely slow. A silent connection is raced by a fresh one and the loser is dropped. None of this depends on whether the app is in the foreground.

W2 · foreground

In the foreground, no dead connection is noticed in under 5 seconds

tdlib's round-trip estimate has a 2 s floor, and the main session's ping timeout is 2.5 of those. On any link, however fast, a silent connection lives at least 5 s, and a read timeout needs 7 s. Download and upload sessions keep the 135 s ping timeout even in the foreground, so they rely on the 7 s read timeout alone.

W3 · reconnects

Every reconnect after an error first spends a round trip on a test ping

For 10 s after any error on an address, tdlib opens new connections in check mode. It opens up to three at a time and sends each a req_pq ping, so a connection only goes to the session after a round trip of its own. On a link that resets, that round trip lands on the calls that were waiting, and the extra connections add handshakes.

What our engine does

A fresh connection carries the waiting calls at once. Its first answer is the proof that it works, and until then it gets a fresh-connection allowance before liveness checks may cut it.

What our engine does

IGE calls the block cipher directly per block, with no per-call dispatch.

W5 · tunnels

A 6 second tunnel costs tdlib 11 seconds in the foreground

On the train link the line goes dark for 6 s every 8–20 s. Live connections survive a tunnel as TCP connections do, and new ones are refused until it ends. tdlib's 5 s ping timeout cuts the connection about a second before the light comes back. Its reconnects in the last dark second are refused, and its foreground flood control (at most five new connections per 5 s) then holds the next attempt back.

04

Taken from tdlib and improved

Gzip only what compresses

Before packing a request of 16 KB or more, tdlib compresses a 1 KB sample from its middle and gives up unless the sample shrinks below 90%. We already skipped file parts by constructor. The sample check now covers every other large incompressible request, such as secret-chat payloads and wrapped calls, without a list.

td/telegram/net/NetQueryCreator.cpp:86–93 → mtproto-core/src/rpc/wrap.rs

if payload.len() >= GZIP_SAMPLE_FROM {          // 16 KB, as tdlib
    let start = (payload.len() - GZIP_SAMPLE_SIZE) / 2;
    let sample = &payload[start..start + GZIP_SAMPLE_SIZE];
    if tlm::gzip(sample).len() * 10 >= GZIP_SAMPLE_SIZE * 9 {
        return None;                               // sent as it is
    }
}

Effect: uploading incompressible 128 KB calls went from 0.14 s to 0.05 s of CPU, level with tdlib.

One quick ack at a time

tdlib never asks for quick acks on upload parts. We asked for one on every large packet: a quick ack tells us when the server has the whole part, which is how we notice an upload stuck on a dead path, something tdlib cannot do. On a lossy downlink, though, every quick ack is one more packet that can stall and hold up the answers behind it.

An answer confirms its packet too, and a quick ack confirms every packet sent before it as well, because one connection is an ordered stream. So a large packet now asks for a quick ack only while no other one is on its way. A resent part still asks for its own, because its answer may be the one to its first copy.

mtproto-core/src/session/mod.rs · awaits_large_quick_ack

let quick_ack_token = if wants_quick_ack
    || (large && (!answer_confirms || !self.awaits_large_quick_ack())) { … }

Same five link seeds, before → after, against tdlib: an upload over lossy-heavy took 28.0 → 26.3 s (tdlib 26.1 s), its typical part 2.02 → 1.71 s (1.68 s), and the slowest calls made during it 2.08 → 1.62 s (1.65 s). Across all 24 upload rows of the weak suite nothing got worse. No call failed, connection counts did not change, and the slowest calls made during an upload improved on edge (3.3 → 2.9 s) and on blackholes (2.6 → 2.0 s).

Limits of this comparison

  • One address per DC. Neither client was offered alternative IPs, IPv6, DC migration or a config update, so tdlib's address rotation in DcOptionsSet was not exercised.
  • Pre-shared permanent key, no PFS. Both engines skip key generation and temporary keys, which tdlib binds on start in production.
  • Replicated connection creator. Proxy selection, network-type changes and multi-DC routing are outside the replica.
  • Loopback throughput is CPU-bound. MB/s on the perfect and fake-TLS rows includes the server's and the link simulator's work on the same machine. CPU seconds per MB is the steadier comparison there.
  • Few probes on fast transfers. mixed/perfect finishes its download in about a tenth of a second, so its probe percentiles rest on 3–4 calls and are not evidence either way.
  • Background mode is a policy. tdlib's long background timers save wakeups by design, and a real app in the background also gets push notifications. The comparison shows the cost of that policy when a path silently dies, not a bug.

Reproduce. tdlib is built with CMake target tdcore; the harness with bench/tdlib-client/build.sh.
