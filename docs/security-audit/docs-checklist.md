# MTProto 2.0 client security requirements (from core.telegram.org only)

Purpose: authoritative checklist for auditing a Rust MTProto client engine. Every entry is sourced from Telegram's official documentation on core.telegram.org (retrieved 2026-10-02, API layer 225). Quotes are verbatim, apart from whitespace normalisation and `\|` escaping inside tables.

Retrieval: each page was fetched raw with curl and converted to text locally, so quotes are not summarised by a model. Raw HTML is in `sec/raw/` and text in `sec/txt/` next to this file, for re-checking.

## Legend

- **Strength**:
  - **MUST**: the doc uses must / required / "is to" / imperative wording.
  - **SHOULD**: the doc uses recommend / should / "would find this useful".
  - **MAY**: the doc says it is optional.
  - **DERIVED**: the doc does not state the check explicitly, but it follows directly from the documented format or semantics. DERIVED rows are marked so the audit can weigh them separately.
- **Severity if violated**:
  - **critical**: breaks confidentiality, integrity or authentication of the session or key.
  - **high**: enables replay, injection, a key-compromise path, memory-safety bugs or account loss.
  - **medium**: a DoS or desync that can be triggered remotely, or an interop break with security impact.
  - **low**: hygiene, or an availability issue with no security impact.
- **Failure action vocabulary** (from security_guidelines#behavior-in-case-of-mismatch, unless a row says otherwise): *discard* means drop the message entirely and use no information from it. *Reconnect* means close and re-establish TCP, then retry the operation or the whole key generation.

## AUTHKEY: authorization key exchange

| ID | Strength | Requirement (precise) | Verbatim quote | Source | Severity (rationale) |
|---|---|---|---|---|---|
| DOC-AUTHKEY-01 | MUST | Start with `req_pq_multi#be7e8ef1 nonce:int128`. `nonce` is 128 bits drawn from a CSPRNG and is unique per handshake run. `req_pq_multi` is the only `req_pq*` function in the current schema. | "The value of nonce is selected randomly by the client (random number) and identifies the client within this communication." | `ak#1-client-sends-query-to-server`, `schema` | high: a predictable nonce lets an attacker pre-compute or correlate a "temporary session". |
| DOC-AUTHKEY-02 | MUST | In `resPQ` and in every later server message of the run (`server_DH_params_ok`, `dh_gen_*`), check that the plaintext `nonce` equals the client's nonce. From `resPQ` on, also check that `server_nonce` equals the value received in `resPQ`. On mismatch, discard and abort the run. | "the client is to check that these fields indeed contain the values previously known." | `sg#checking-nonce-server-nonce-and-new-nonce-fields` | critical: binds every message to this run and prevents splicing parallel runs. |
| DOC-AUTHKEY-03 | MUST | The same (nonce, server_nonce) check applies inside the encrypted portions: the decrypted `server_DH_inner_data.nonce` and `.server_nonce` must equal the known values. | "All subsequent messages contain the pair (nonce, server_nonce) both in the plain-text, and the encrypted portions which makes it possible to identify a “temporary session”" | `ak#2-server-sends-response-of-the-form` | critical: stops reuse of server-encrypted blobs across runs. |
| DOC-AUTHKEY-04 | MUST / DERIVED | `pq` is a big-endian byte string. It is a product of two *different odd primes*, normally ≤ 2^63−1. The client factors it into `p < q`, sends `p` and `q` as big-endian strings, and uses identical `pq`/`p`/`q` in `req_DH_params` and `p_q_inner_data*`. DERIVED: verify `p*q == pq` and `p < q`, and reject oversized `pq` (more than 64 bits) before factoring, to bound CPU use. | "This number is the product of two different odd prime numbers. Normally, pq is less than or equal to 2^63-1." / "Client decomposes pq into prime factors such that p < q." | `ak#2-server-sends-response-of-the-form`, `ak#3-client-decomposes-pq-into-prime-factors-such-that-p-lt-q` | medium: a malicious peer can send a huge `pq` and burn CPU (DoS). |
| DOC-AUTHKEY-05 | MUST | Server authentication. Pick an RSA key whose fingerprint appears in `server_public_key_fingerprints` **and** is one of the client's built-in (or, for CDN DCs, `help.getCdnConfig`) public keys. The fingerprint is the lower 64 bits of SHA1 over the TL bare `rsa_public_key n:string e:string`, with n and e big-endian. If no fingerprint matches, abort (never trust a key supplied by the server). | "server_public_key_fingerprints is a list of public RSA key fingerprints (64 lower-order bits of SHA1 (server_public_key); the public key is represented as a bare type rsa_public_key n:string e:string = RSAPublicKey" / "The application has a built-in public server key" | `ak#2-server-sends-response-of-the-form`, `desc#server-key`, `faq#q-how-is-the-server-authenticated-during-dh-key-exchange`, `sak` ("Let's choose the only matching key") | critical: the RSA key is the only MITM protection of the handshake. |
| DOC-AUTHKEY-06 | MUST | `new_nonce` is 256 bits from a CSPRNG. It is sent only inside the RSA-encrypted `p_q_inner_data*` and never in clear. All later handshake crypto depends on it. | "new_nonce := another (good) random number generated by the client" / "Notice that new_nonce is transferred explicitly only once, inside an RSA-encrypted message from the client to the server." | `ak#4-encrypted-data-payload-generation`, `faq#q-how-are-clients-authenticated` | critical: knowing `new_nonce` lets an attacker forge server replies and derive the temp AES keys. |
| DOC-AUTHKEY-07 | MUST | `p_q_inner_data_dc#a9f55f95` is for permanent keys and `p_q_inner_data_temp_dc#56fddf88` (with `expires_in`) is for temp keys. `dc` is the target DC ID: add 10000 for test DCs, and negate it for media (not CDN) DCs. A test/prod mismatch yields transport error −444. | "`10000` has to be added to the DC ID when connecting to the test servers; it has to be made negative if the DC we're connecting to is a media (not CDN) DC." | `ak#4-encrypted-data-payload-generation`, `ak#6-server-responds-with` | medium: a wrong DC binding or test/prod confusion causes handshake failure or keys bound to the wrong environment. |
| DOC-AUTHKEY-08 | MUST | RSA_PAD step 1. Serialized `data` must be ≤ 144 bytes. Append random bytes to reach exactly 192 bytes (`data_with_padding`), then byte-reverse it (`data_pad_reversed`). | "One has to check that data is not longer than 144 bytes." / "random_padding_bytes are chosen so that the resulting length of data_with_padding is precisely 192 bytes" | `ak#41-rsa-paddata-server-public-key-mentioned-above-is-implemented-as-follows` | high: overlong data or a non-random pad breaks the OAEP+-like padding security. |
| DOC-AUTHKEY-09 | MUST | RSA_PAD step 2. Generate a random 32-byte `temp_key`. Compute `data_with_hash = data_pad_reversed ‖ SHA256(temp_key ‖ data_with_padding)` (224 bytes) and `aes_encrypted = AES256_IGE(data_with_hash, temp_key, IV=0)`. Then `temp_key_xor = temp_key XOR SHA256(aes_encrypted)` and `key_aes_encrypted = temp_key_xor ‖ aes_encrypted` (256 bytes). | "data_with_hash := data_pad_reversed + SHA256(temp_key + data_with_padding); -- after this assignment, data_with_hash is exactly 224 bytes long." / "temp_key_xor := temp_key XOR SHA256(aes_encrypted)" | `ak#41-...` | high: deviation breaks the padding scheme that protects `new_nonce`. |
| DOC-AUTHKEY-10 | MUST | RSA_PAD step 3. If `key_aes_encrypted` ≥ the RSA modulus (compared as a 256-byte big-endian integer), regenerate `temp_key` and repeat. Raw RSA output must be exactly 256 bytes big-endian, with leading zeros where needed. | "If key_aes_encrypted turns out to be greater than or equal to the RSA modulus, the previous steps starting from the generation of new random temp_key are repeated." / "the result is stored as a big-endian integer consisting of exactly 256 bytes (with leading zero bytes if required)." | `ak#41-...` | high: an incorrect modular reduction or length leaks structure or causes intermittent failures. |
| DOC-AUTHKEY-11 | MUST | Decrypt `server_DH_params_ok.encrypted_answer` with AES-256-IGE using `tmp_aes_key = SHA1(new_nonce‖server_nonce) ‖ substr(SHA1(server_nonce‖new_nonce),0,12)` and `tmp_aes_iv = substr(SHA1(server_nonce‖new_nonce),12,8) ‖ SHA1(new_nonce‖new_nonce) ‖ substr(new_nonce,0,4)`. | "tmp_aes_key := SHA1(new_nonce + server_nonce) + substr (SHA1(server_nonce + new_nonce), 0, 12);" | `ak#6-server-responds-with` | critical: the derivation is what proves the reply came from the holder of the RSA private key. |
| DOC-AUTHKEY-12 | MUST / DERIVED | After decrypting, verify `answer_with_hash = SHA1(answer) ‖ answer ‖ pad(0–15)`. The first 20 bytes MUST equal SHA1 of the TL-parsed `server_DH_inner_data` without the random tail. DERIVED: the ciphertext length must be a multiple of 16, the tail length must be in 0..15, and the parse must stay within the buffer. On failure, discard and restart the handshake. | "the first 20 bytes of `answer_with_hash` must be equal to SHA1 of the remainder of the decrypted message without the padding random bytes." | `sg#checking-sha1-hash-values-during-key-generation` | critical: this is the integrity check on `g`, `dh_prime`, `g_a` and `server_time`. |
| DOC-AUTHKEY-13 | MUST | Handshake transport errors: −404 means the query was incorrect, so restart the handshake from step 1 (every later request also gets −404). −444 means a test DC ID was used against prod or the reverse. | "If the query is incorrect, the server returns a `-404` error and the handshake must be restarted (any subsequent request also returns `-404`, even if it is correct)." | `ak#6-server-responds-with` | medium: retrying the same run forever is a DoS or hang. |
| DOC-AUTHKEY-14 | MUST | `dh_prime` must be a safe 2048-bit prime: p and (p−1)/2 both prime, and 2^2047 < p < 2^2048. | "Client is expected to check whether p = dh_prime is a safe 2048-bit prime (meaning that both p and (p-1)/2 are prime, and that 2^2047 < p < 2^2048)" | `ak#6-server-responds-with`, `sg#validation-of-dh-parameters` | critical: a weak or composite p allows small-subgroup or discrete-log recovery of `auth_key`. |
| DOC-AUTHKEY-15 | MUST | `g` ∈ {2,3,4,5,6,7} and must be a quadratic residue mod p, so that it generates the subgroup of prime order (p−1)/2. The conditions are: g=2 needs p mod 8 = 7; g=3 needs p mod 3 = 2; g=4 has no condition; g=5 needs p mod 5 ∈ {1,4}; g=6 needs p mod 24 ∈ {19,23}; g=7 needs p mod 7 ∈ {3,5,6}. | "p mod 8 = 7 for g = 2; p mod 3 = 2 for g = 3; no extra condition for g = 4; p mod 5 = 1 or 4 for g = 5; p mod 24 = 19 or 23 for g = 6; and p mod 7 = 3, 5 or 6 for g = 7." | `ak#6-server-responds-with`, `sg#validation-of-dh-parameters` | critical: a non-residue g leaks one bit of the exponent and permits subgroup confinement. |
| DOC-AUTHKEY-16 | MAY | Ways to speed up primality checking: cache verified (g,p) pairs; start with 15 Miller–Rabin rounds (error ≤ 10^-9) and run more in the background; or embed a table of known-good primes. The current `dh_prime` is published as C7 1C AE B9 ... 2F CC 5B. If the check is cached, the cache key must be the full p (DERIVED). | "one might initially run only 15 Miller--Rabin iterations ... with error probability not exceeding one billionth, and do more iterations later in the background." / "embed into the client application code a small table with some known \"good\" couples (g,p)" | `ak#6-...`, `sg#validation-of-dh-parameters` | medium: a cache keyed by something weaker than the full p re-opens AUTHKEY-14. |
| DOC-AUTHKEY-17 | MUST + SHOULD | MUST: 1 < g < p−1 and 1 < g_a < p−1. SHOULD: 2^(2048−64) ≤ g_a ≤ p − 2^(2048−64). | "both sides are to check that g, g_a and g_b are greater than 1 and less than dh_prime - 1. We recommend checking that g_a and g_b are between 2^{2048-64} and dh_prime - 2^{2048-64} as well." | `ak#9-server-responds-in-one-of-three-ways` ("IMPORTANT"), `sg#g-a-and-g-b-validation` | critical: g_a ∈ {0,1,p−1} forces a known `auth_key`. |
| DOC-AUTHKEY-18 | MUST | The client's own `g_b = g^b mod p` must satisfy the same bounds. If it does not, regenerate `b`. ("both sides are to check".) | "both sides are to check that g, g_a and g_b are greater than 1 and less than dh_prime - 1." | `sg#g-a-and-g-b-validation` | high: a degenerate g_b weakens the key. |
| DOC-AUTHKEY-19 | MUST | `b` is a 2048-bit secret from a CSPRNG with sufficient entropy. Server-provided "random" bytes may only be **mixed** into the local PRNG, never used alone or as a replacement seed. | "Client must use a cryptographically secure PRNG to generate secret exponents `a` or `b` for DH key exchange." / "never using these \"random\" bytes by themselves or replacing by them the local PRNG seed. One should mix bytes received from server into local PRNG seed." | `sg#using-secure-pseudorandom-number-generator-to-create-dh-secret-parameters-a-and-b`, `ak#7-...` | critical: a predictable b gives the attacker `auth_key`. |
| DOC-AUTHKEY-20 | MUST | `set_client_DH_params#f5045f1f`. Its `encrypted_data` = AES256-IGE(tmp_aes_key, tmp_aes_iv) of `SHA1(data) ‖ data ‖ 0–15 random bytes`, padded to a multiple of 16, where `data = client_DH_inner_data#6643b654 nonce server_nonce retry_id g_b`. `retry_id = 0` on the first attempt, otherwise the `auth_key_aux_hash` of the previous failed attempt. | "The retry_id field is equal to zero at the time of the first attempt; otherwise, it is equal to auth_key_aux_hash from the previous failed attempt" | `ak#7-...` | medium: a wrong retry_id or hash breaks retries; a non-random pad is minor. |
| DOC-AUTHKEY-21 | MUST / DERIVED | `auth_key = g_a^b mod p`. `auth_key_id` (= auth_key_hash) is the lower 64 bits of SHA1(auth_key), i.e. the last 8 bytes of the digest. `auth_key_aux_hash` is the higher 64 bits (first 8 bytes) and must not be confused with it. DERIVED (from the secret-chat page): `auth_key` is handled as exactly 256 bytes, left-padded with zeros. | "Auth_key_hash is computed := 64 lower-order bits of SHA1 (auth_key)." / "auth_key_aux_hash is the 64 higher-order bits of SHA1(auth_key). It must not be confused with auth_key_hash." / (e2e) "If key length < 256 bytes, add several leading zero bytes as padding" | `ak#8-...`, `ak#9-...`, `e2e` | high: a wrong byte layout gives a wrong key or id. That is interop-fatal, and inconsistent handling can leak timing. |
| DOC-AUTHKEY-22 | MUST | `dh_gen_ok/retry/fail`. Verify nonce and server_nonce, and `new_nonce_hashN = lower 128 bits of SHA1(new_nonce ‖ byte(N) ‖ auth_key_aux_hash)`, with N = 1 for ok, 2 for retry, 3 for fail. Accept the key only if `dh_gen_ok` carries a valid `new_nonce_hash1`. | "new_nonce_hash1, new_nonce_hash2, and new_nonce_hash3 are obtained as the 128 lower-order bits of SHA1 of the byte string derived from the new_nonce string by adding a single byte with the value of 1, 2, or 3, and followed by another 8 bytes with auth_key_aux_hash. Different values are required to prevent an intruder from changing server response dh_gen_ok into dh_gen_retry." | `ak#9-server-responds-in-one-of-three-ways` | critical: this is the key-confirmation step and stops ok/retry/fail substitution. |
| DOC-AUTHKEY-23 | MUST / DERIVED | `dh_gen_retry` (verified) means go back to step 7 with a **new** `b` and `retry_id = auth_key_aux_hash`. DERIVED: on `dh_gen_fail`, or on any check failure, abort and restart from step 1. | "In the other case, the client goes to Item 7) generating a new b." | `ak#9-...` | medium: reusing b, or looping, is a DoS or weakens the key. |
| DOC-AUTHKEY-24 | MUST | After `dh_gen_ok`, forget all temporary data (b, new_nonce, tmp_aes_key/iv). The initial `server_salt = substr(new_nonce,0,8) XOR substr(server_nonce,0,8)`. Store the difference between `server_time` and local time to generate msg_ids. | "the client and the server have negotiated auth_key, following which they forget all other temporary data ... server_salt is initially set to `substr(new_nonce, 0, 8) XOR substr(server_nonce, 0, 8)`." | `ak#9-...` | medium: leftover secrets increase the impact of a later compromise; a wrong salt causes extra round trips. |
| DOC-AUTHKEY-25 | MUST | Handshake retransmission. Re-send only *byte-identical* queries; the server caches responses for up to 10 minutes. If the server has forgotten the state, restart from the beginning. | "exactly the same request and not just similar: all the parameters during the repeat request must take on the same values" / "The server remembers the response for up to 10 minutes" | `ak#error-handling-lost-queries-and-responses` | low: sending a changed retry with the same nonces can confuse state. |
| DOC-AUTHKEY-26 | MUST | Handshake messages are unencrypted: `auth_key_id=0 (int64) ‖ msg_id (int64) ‖ message_data_length (int32) ‖ message_data`. Only a very limited set of messages may be sent this way. The client's msg_ids still follow the msg_id rules (see MSG-09). | "Special plain-text messages may be used to create an authorization key as well as to perform a time synchronization. They begin with auth_key_id = 0" / "Only a very limited number of messages of special types can be transmitted as plain text." | `desc#unencrypted-messages`, `desc#unencrypted-message` | medium: see MSG-01 for accepting plaintext outside the handshake. |
| DOC-AUTHKEY-27 | MUST | Byte order. RSA/DH numbers (`pq`, `p`, `q`, `dh_prime`, `g_a`, `g_b`) are big-endian byte strings. TL ints are little-endian. SHA1 outputs are byte strings, so a `long` taken from SHA1 is its final 8 bytes read as a 64-bit integer, with no byte rearrangement. | "very large numbers (2048-bit or `pq`, `p`, `q` params) used in RSA and DH are written in the big endian format" / "if `long` `x` is the 64 lower-order bits of SHA1 of string `s`, then the final 8 bytes of 20-byte string `SHA1(s)` are taken" | `mtproto#high-level-component-rpc-query-language-api`, `ak` (intro) | high: an endianness bug produces wrong keys or ids. Checks then fail open or fail closed. |
| DOC-AUTHKEY-28 | MUST | An `auth_key_id` collision is resolved by regenerating the key. The server reports this via `dh_gen_retry`. | "Keys must be uniquely defined by the 64 lower-order bits of their SHA1, and in the event of a collision, an authorization key is regenerated." | `desc#key-identifier-auth-key-id` | low: handled by AUTHKEY-23. |
| DOC-AUTHKEY-29 | MUST | After `dh_gen_ok`, the client creates an encrypted session with a fresh random `session_id`. All further traffic, including registration and phone verification, runs inside that encrypted session. | "The client then creates an encrypted session using the newly generated key, and subsequent communication occurs within that session" | `desc#creating-an-authorization-key` | medium: no API traffic is allowed in plaintext. |

## Things the docs say clients must NOT do (consolidated)

1. Never use the permanent auth_key_id directly when PFS is in use (PFS-02). Never use an unbound temp key for anything except bind, getConfig and getNearestDc (PFS-03).
2. Never use any information from a message that failed a check. Never return a different response or behaviour for a pre-msg_key error than for a msg_key failure (MSG-18, CRYPTO-06).
3. Never access data past the end of the decryption buffer (MSG-03).
4. Never mark `msgs_ack`, `msg_container`, `msg_copy` or `gzip_packed` as content-related. Never mark an RPC query as non-content-related (MSG-13).
5. Never re-send a message on its own with the same msg_id (MSG-11). Never reuse a container msg_id (MSG-10).
6. Never send a message meant for one session into another session (MSG-04).
7. Never use server-provided randomness alone or as a seed replacement (AUTHKEY-19, OTHER-09).
8. Never confuse `auth_key_aux_hash` with `auth_key_hash`/`auth_key_id` (AUTHKEY-21).
9. Never mix MTProto 1.0 and 2.0 on one TCP connection (CRYPTO-07).
10. Never update server_salt or the clock from a notification or response that does not match a recently sent query (SVC-02, SVC-03).
11. CDNs:
    - never accept updates from a CDN DC (CDN-03);
    - never let a CDN substitute replies to other DCs' queries (CDN-04);
    - never send private initConnection info to a CDN (CDN-05);
    - never save CDN data before its hash verifies (CDN-02);
    - never handshake with a CDN whose RSA key is not in `help.getCdnConfig` (CDN-01).
12. Never handle updates from unencrypted connections (OTHER-02).
13. Never open more main sessions than `tmp_sessions` allows (OTHER-04).
14. Obfuscation:
    - never send the stand-alone protocol header after an obfuscated init (TRANSPORT-10);
    - never reset the CTR stream between packets (TRANSPORT-12);
    - never pick an init whose prefixes collide with known protocol headers (TRANSPORT-09).
15. With `this_port_only`, never try other ports (TRANSPORT-15).
16. Never use the published example MTProxy secret on a public proxy (PROXY-06).
17. Never send `http_wait` over anything other than HTTP (SVC-22).

## Historical attacks and mitigations as documented

| Topic | What the docs say | Required mitigation (where in this checklist) | Source |
|---|---|---|---|
| MTProto 1.0 not IND-CCA (padding unauthenticated) | v1.0 computed msg_key = lower 128 bits of SHA-1(plaintext **excluding padding**). "under certain circumstances a ciphertext could be modified so that it would have been accepted and decrypted to the same plaintext as the original unmodified ciphertext." | 2.0 changes: SHA-256; padding included in msg_key; msg_key depends on an auth_key fragment; 12..1024 padding bytes (CRYPTO-01, CRYPTO-04, CRYPTO-05, MSG-02). "MTProto 2.0 satisfies the conditions for indistinguishability under chosen ciphertext attack (IND-CCA)." | `/techfaq/mtproto_v1#what-about-ind-cca`, `desc` (principal differences), `faq#what-about-ind-cca` |
| SHA-1 weaknesses | v1.0 used SHA-1 for the KDF and msg_key. In 2.0, SHA-256 is used in all critical places, and SHA-1 is kept only for the handshake, auth_key_id and fingerprints. | CRYPTO-13 | `/techfaq/mtproto_v1#q-why-did-you-use-sha-1-sha-1-is-broken`, `faq#q-do-you-still-use-sha-1` |
| Error-path / timing oracle around msg_key | The docs require the msg_key check to run even after an earlier error, with an identical response (present in both the v1 and v2 guidelines). The docs do not name an attack or paper here. | CRYPTO-06, CRYPTO-10 | `sg#checking-sha256-hash-value-of-msg-key`, `/mtproto/security_guidelines_v1` |
| IGE blockwise-adaptive CPA | IGE, like CBC, is vulnerable to blockwise-adaptive CPA. The attack is ruled out because the key depends on the full message (via msg_key), so adaptive attacks are "theoretically impossible". IGE is not used as a MAC. | CRYPTO-01..05 (never reuse aes_key/iv across messages; never MAC with IGE) | `faq#q-do-you-use-ige-ige-is-broken`, `faq#chosen-plaintext-attacks` |
| Length-extension | msg_key is over the plaintext, not the ciphertext. Changing msg_key changes the AES key, so the message decrypts to garbage and fails the check. | CRYPTO-05 | `faq#length-extension-attacks` |
| Replay | Defeated by salt + unique msg_id + seqno inside the authenticated plaintext. v1.0 docs warned that the server would start ignoring msg_ids whose lower 32 bits contain "too many zeroes". The salt grace period changed from 300 s (v1, 24 h rotation) to 1800 s (v2, 30 min rotation). | MSG-05..09, MSG-16, SVC-02/03 | `faq#replay-attacks`, `/mtproto/description_v1#message-identifier-msg-id`, `desc#server-salt` |
| MITM on DH key exchange | Prevented only by the server RSA key embedded in the client. | AUTHKEY-05, CDN-01, PROXY-05 | `faq#man-in-the-middle-attacks` |
| DH fingerprint collisions (secret chats) | The 128-bit fingerprint was theoretically spoofable. The current 288-bit visualisation is 128 bits of SHA-1 plus 160 bits of SHA-256. This concerns only the secret-chat UI, not the cloud transport. | n/a for the cloud transport | `/techfaq/mtproto_v1#hash-collisions-for-diffie-hellman-keys`, `faq#hash-collisions-for-diffie-hellman-keys` |
| Small-subgroup / weak DH parameters | Implied by the safe-prime, generator and g_a range checks. | AUTHKEY-14..18 | `sg#diffie-hellman-key-exchange` |

Note: core.telegram.org does not cite any academic paper by name (for example Jakobsen–Orlandi 2015/16 or Albrecht–Mareková–Paterson–Stepanovs 2021/22). The IND-CCA passage above is Telegram's own description of the v1.0 issue. The "same response for any pre-msg_key error" rule is the documented mitigation for error/timing oracles, but the docs do not attribute it to a specific attack.

## Gaps: what the official docs do not specify (audit these against reference implementations)

1. **N** for the msg_id replay window (MSG-06) is unspecified.
2. **Fake-TLS / "ee" MTProxy secrets** have no core.telegram.org specification (PROXY-04).
3. There is no maximum transport packet size and no maximum decompressed `gzip_packed` size (SVC-16).
4. CRC32 and seq verification for the **Full** transport is not stated as a client check (TRANSPORT-05).
5. Constant-time comparison is not mentioned explicitly (CRYPTO-10).
6. Whether the CDN `FileHash` covers the encrypted or the decrypted bytes is ambiguous. /cdn says "Encrypted file fragments are protected from tampering by their SHA-256 hash", while `fileHash` says "SHA-256 Hash of an uploaded file". Confirm against tdlib or tdesktop before auditing CDN-02.
7. Left-padding of `auth_key` to 256 bytes is stated only on the secret-chat page (AUTHKEY-21).
8. Whether to adopt `new_session_created.server_salt` is not stated explicitly.
9. No bound is given on `pq` size or factorisation time (AUTHKEY-04).
10. No plausibility check is specified for `server_time` in `server_DH_inner_data`.
11. The schema no longer contains `server_DH_params_fail`. The only documented handshake failure signals are transport −404/−444, `dh_gen_retry` and `dh_gen_fail`.
12. How to treat an unauthenticated −404 or −444 on an established permanent key (as opposed to temp or CDN keys) is not specified. Since transport errors are unauthenticated, an injected −404 must not trigger destructive key deletion (TRANSPORT-07).

## Ten most critical requirements (auditor's judgement)

1. **DOC-CRYPTO-05 + DOC-CRYPTO-06**: verify msg_key (SHA-256 with x = 8, over plaintext including padding) on every inbound message, with identical behaviour for every pre-check error.
2. **DOC-MSG-02 + DOC-MSG-03**: length ≤ plaintext−32, padding in 12..1024, length non-negative and a multiple of 4, no reads past the buffer.
3. **DOC-AUTHKEY-05**: RSA fingerprint must match a pinned built-in key (and **DOC-CDN-01**: the CDN key must come from `help.getCdnConfig`). This is the only MITM barrier.
4. **DOC-AUTHKEY-14 + DOC-AUTHKEY-15**: dh_prime is a safe 2048-bit prime, and g ∈ {2..7} is a quadratic residue mod p.
5. **DOC-AUTHKEY-17 + DOC-AUTHKEY-18**: 1 < g, g_a, g_b < p−1, and (recommended) within [2^1984, p−2^1984].
6. **DOC-AUTHKEY-22 + DOC-AUTHKEY-02/03**: nonce and server_nonce match in every step (plain and encrypted), and new_nonce_hash1/2/3 is verified with the correct N.
7. **DOC-AUTHKEY-12**: the SHA1 check of `answer_with_hash` on server_DH_inner_data.
8. **DOC-AUTHKEY-19 / DOC-AUTHKEY-06 / DOC-OTHER-09**: CSPRNG for nonce, new_nonce, b and padding, with server entropy only mixed in.
9. **DOC-MSG-04 + DOC-MSG-05 + DOC-MSG-06 (+ SVC-02/03)**: session_id must match; server msg_id must be odd; replay set; salt and time updated only from verified, recently sent msg_ids.
10. **DOC-CDN-02 (+ CDN-03/04)**: per-part SHA-256 verification against master-DC hashes before saving; no updates from CDNs and no reply substitution across DCs.

Close runners-up: DOC-PFS-02 (never use the perm key directly under PFS), DOC-MSG-18 (discard on any failure), DOC-OTHER-02 (ignore updates on unencrypted connections), DOC-TRANSPORT-12 (continuous CTR stream).
