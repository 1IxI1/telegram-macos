## Conventions

**Paths.** `core/` = `crates/mtproto-core/src/`, `eng/` = `crates/mtproto-engine/src/`, `ts/` = `crates/mtproto-testserver/src/`, `fz` = `crates/mtproto-fuzz/src/targets.rs`, `swift/` = `submodules/MTProtoRustEngine/Sources/`.

**Tests.** `msg-t` = `core/message.rs` tests, `kdf-t` = `core/crypto/kdf.rs` tests, `ige-t` / `ctr-t` = `core/crypto/aes_ige.rs` / `aes_ctr.rs` tests, `sess-t` = `core/session/tests.rs`, `codec-t` = `core/transport/codec.rs` tests, `obf-t` = `core/transport/obfuscation.rs` tests, `rd-t` = `core/tl/reader.rs` tests, `tl-t` = `core/tl/mtproto.rs` tests, `eng-t` = `crates/mtproto-engine/tests/engine.rs`, `rpc-t` = `core/rpc/tests.rs`, `ffi-t` = `crates/mtproto-ffi/tests/ffi.rs`, `FZ:x` = fuzz target `x`.

**Attackers.** NET = on-path attacker without the auth key. On a direct connection the obfuscation keys are derived from the client's 64-byte init, which travels in the clear (only bytes 56..64 are encrypted), so NET can read, delete, delay and inject whole frames in both directions. Any SOCKS5 relay has the same power; an MTProxy operator has it too because it knows the secret. SRV = holder of the auth key (the server). HOST = the Swift caller of the C ABI.

**Verdicts.** OK, PARTIAL, MISSING, DEVIATION (deliberate, documented in `docs/protocol-coverage.md`), BETTER (than tdlib), N/A (not the engine's job; owner named).

**Bench hosts** (where a BENCH CASE can be written today):

### Medium

**M1. An unauthenticated −404 discards the session and replays every in-flight request in a new session (F1).**
- Code: `core/transport/codec.rs:280-283` (any 4-byte short frame is a code); `eng/session_runtime.rs:1284-1288,1313-1320` (`AuthKeyInvalid`, `self.rpc.take()`, all requests requeued through `core/rpc/mod.rs:832-841`); `eng/session_runtime.rs:243-279` (the next key, even the same one, gets `Session::new` with a new session_id); host `swift/MTProtoRustEngine/RustNetworkSession.swift:522-526,826-871`, `swift/MTProtoRustEngineMapping/RustEngineMapping.swift:203-213`.
- Who: NET on any direct connection, any SOCKS5 relay, any MTProxy operator. One frame (abridged `01 6c fe ff ff`).
- Scenario: the user sends X (for example `messages.createChat` or `channels.createChannel`, which carry no `random_id`). The server executes X. The attacker injects −404 before the answer. The engine drops its RpcClient; the genuine answer later arrives for the old session_id and is ignored as `ForeignSession`. The host then re-installs the same persistent key (`checkIfLoggedOut`), regenerates and re-binds a temp key, or (foreign-DC workers) deletes the auth token and re-imports authorization. All requests are re-sent under a new session_id, which the server cannot deduplicate, so X runs twice. Repeating the frame on every connection keeps the client in DH-handshake, bind and export/import churn.
- Context: tdlib also re-sends in-flight queries after a PFS −404 (via `new_session_created`), but for a non-PFS key its first −404 only switches to a PFS probe and keeps the session. The coverage doc (T01/P01) calls the replay intentional; on merit it turns a forgeable 4-byte frame into duplicate execution. The exactly-once hostile suite excludes −404 (`ts/lib.rs:1080`), so nothing catches it.
- Fix: (1) on −404 park the RpcClient instead of `take()`; if the host re-installs the same key id, resume the same session (in-flight queries become Unknown and go through `msgs_state_req`), never `Session::new`. (2) When the key really changes, requeue only requests that were never sent, and report in-flight ones (`may_have_arrived`) to the host as "outcome unknown" so non-idempotent calls are not replayed blindly. (3) Confirm before acting: treat the key as invalid only if −404 repeats on a fresh connection before any authenticated packet, and rate-limit invalidations per DC (for example one per 60 s). (4) Add −404 after execution to `HostileTransportCode`, with host emulation, to the exactly-once suite.

### Low

**L1. Evicted (TooOld) replays can set the clock whenever the session is unsynchronized (F4, refined).**
- Code: `core/session/mod.rs:1205-1219` (`Mode::Replay` reaches `observe_server_time` at `:1212`), `:1265-1268`, `:1308-1318`, `:1320-1326`; reset sources `:1217,1584,1588,1616,1672`; host `swift/MTProtoRustEngine/RustNetworkSession.swift:541-542` (`setGlobalTimeDifference`).
- Scenario: NET records server packet P of session S. Hours later, once P has been evicted from the 1000–2000-id window, the attacker waits for or provokes a clock reset. It can provoke one by delaying a client packet by more than 300 s, which earns a genuine `bad_msg_notification 16`, or through L3. It then injects P. P is `TooOld`, `observe_server_time` sets the offset to P's time, the window passes, P is processed in Replay mode, and `TimeDifferenceUpdated` moves the MTContext global time difference (used by TelegramCore and by new sessions) back by hours. The next genuine packet fixes it. tdlib runs the duplicate check before `update_server_time_difference` (`AuthData.cpp:153-156`), so its code-2 packets never touch the clock.
- Fix: call `observe_server_time` only for `Mode::Process`; when `!time_synchronized`, drop `Mode::Replay` packets unless they carry a freshness proof; never let Replay packets move the clock.

**L2. Message ids below the duplicate window are processed instead of ignored (F3; cov D10).**
- Code: `core/session/dedupe.rs:26-28,55-57`; `core/session/mod.rs:1205-1209,1403-1405,1484-1488,1498-1510`.
- Scenario: in a busy session, NET replays evicted server packets that are still within 300 s. Each is acked and each update in it yields `UpdatesLost`, so every injected packet costs the client a `getDifference` round trip. Integrity holds: actions are limited to live state.
- Fix: keep the replay-safe completion of live rpc_results, but rate-limit `UpdatesLost` from Replay mode and keep Replay packets away from the clock (L1). Alternatively ignore them as the docs say.

**L3. The freshness proof accepts arbitrarily old answers as proof of a wrong clock (F5).**
- Code: `core/session/mod.rs:1294,1302` (`by_msg_id.contains_key`, no recency check), `:1217` (forced reset); compare `:1298-1303` (`was_sent_recently`).
- Scenario: NET withholds the genuine answer to a query (and deletes the server's redeliveries) for more than 300 s, then delivers it. The answer is accepted, which is correct, but it also forces the clock back to its msg_id and unsynchronizes the session, which opens L1.
- Fix: complete the live query, but count it as a clock proof only if the request was sent within the window (`was_sent_recently(req_msg_id)`). Otherwise process it without resetting the clock.

**L4. Frame-progress liveness lets an on-path attacker stall a session for hours (new).**
- Code: `eng/session_runtime.rs:27-28` (15 s grace, 512 B/s), `:1068-1075` (`note_bytes_received` + `last_progress_at` while a frame is progressing), `:1128-1144`; `core/session/mod.rs:614-618,1956-1966` (ping, read and probe timeouts all keyed on `last_read_at`); request timeout `eng/session_runtime.rs:1490-1498` (keyed on `last_progress_at`; the host sets 5 s, `swift/MTProtoRustEngine/RustNetworkSession.swift:198`); cap `core/transport/codec.rs:5` (16 MiB).
- Scenario: NET or a proxy operator sends a frame header that declares 16 MiB, then ≥ 512 B/s of filler. None of the ping, read, probe or request timeouts fire for up to 16 MiB / 512 B/s ≈ 9.1 h. The app looks connected, no request completes, and failover to other addresses or proxies never starts. Only at the end does the MAC fail. tdlib resets its read timeout on any byte, so it is weaker; the engine's own L10 fix covers only rates below 512 B/s, and its test trickles at about 3 B/s.
- Fix: bound the total time any one frame may take, for example `min(max(15 s, length / 64 KiB/s), 120 s)`, or require a rate that scales with the declared length. Lower the inbound cap to tdlib's `(1 << 22) + 1024`; legitimate server frames are file parts of about 1 MiB.

**L5. Weak length hiding on direct connections (no size buckets) (new versus TD-CRYPTO-15; cov I07 calls it deliberate).**
- Code: `core/message.rs:67-77`; `eng/session_runtime.rs:36-37,232-241`.
- Scenario: passive NET derives the obfuscation keys from the clear init and reads exact frame lengths. With 0–64 B of random padding, sizes leak at about 16-byte granularity, which allows traffic classification (text lengths, typing and read events). tdlib rounds to 64…1280 B and then 448-byte steps.
- Fix: on direct connections, round the encrypted size up to tdlib's bucket table (`Transport.cpp:166-197`) and keep the random extra blocks on top.

**L6. HOST-reachable aborts from writer and frame assertions (F18).**
- Code: `core/tl/writer.rs:79,91`; `core/tl/mtproto.rs:735,783,787`; `core/transport/codec.rs:42-43`; `core/rpc/wrap.rs:39-91` writes host strings after the 8 MiB body check at `core/rpc/mod.rs:296-305`.
- Scenario: a host bug that passes a 16 MiB device string, params blob or token, or an 8 MiB body plus large params, aborts the app (`panic = "abort"`).
- Fix: validate the wrapped size in `wrap_request` and at the FFI boundary, and fail the request locally with `REQUEST_INVALID_SIZE`.

### Info

- **I1 (F2).** The +30 s bound is never enforced, because `observe_server_time` raises the clock first (`core/session/mod.rs:1212-1213,1308-1318`). SRV-only; identical to tdlib (`AuthData.cpp:156-164`). Optional fix: enforce +30 s once synchronized and recover through a freshness proof, as the engine already does for the past.
- **I2 (new). Errors are not sticky.** After a MAC failure, a transport error or a handshake failure, `handle_io` calls `process_incoming` again over the rest of the buffered frames before closing (`eng/session_runtime.rs:1089-1096`; errors returned at `:1229,1273,1287`). Valid packets after a forged one are applied, and a second −404 re-emits `AuthKeyInvalid` while the host's `installedKeyId` is already nil. Fix: have `process_incoming` return a distinct protocol error, and drain buffered frames only on EOF or I/O errors.
- **I3 (new). Silent update loss on engine-side drops.** Messages dropped for depth > 8, more than 4096 per packet, gzip failure or an exhausted unpack budget are acked and recorded but raise no `UpdatesLost` (`core/session/mod.rs:1356-1371,1413-1417,1516`). SRV-only. Fix: set `context.updates_lost` when a dropped message is not provably service-only.
- **I4 (F8). Quick-ack forgery.** Downgraded; see the corrections below. Hardening: let quick acks drive only the `Acknowledged` UI event and keep `acknowledged`, which suppresses retransmission (`core/session/mod.rs:816`), for authenticated `msgs_ack`.
- **I5 (F21).** Up to 15 unauthenticated trailing bytes are ignored (`core/message.rs:131`; `core/transport/codec.rs:288-291`). Same as tdlib.
- **I6 (F22, F6, F7).** Foreign-session and even-id packets are dropped without closing; children get no per-child time window and no check that their id is below the container's; incoming salt and seqno are not checked. All SRV-only and same as tdlib.
- **I7 (F9).** `progress_target` decrypts unauthenticated frame heads (`core/session/mod.rs:1171-1192`; `eng/session_runtime.rs:1338-1366`). Progress events can be spoofed only by replaying the genuine head of an answer to a pending query. UI-only.
- **I8.** TL lenience: service objects need not end exactly, and boxed/bare variants are tolerated (TD-TL-5). SRV-only.
- **I9 (F15).** Dead MTProto 1.0 crypto ships in the library; `decrypt_message_v1` reads the length before checking the SHA-1 MAC (`core/message.rs:175-233`).
- **I10 (F20).** There are no external known-answer vectors for IGE, KDF2, msg_key or tmp_aes.
- **I11 (F23).** `seq_no += 2` on an i32 does not saturate (`core/session/mod.rs:688`).
- **I12 (F17).** `constant_time_eq` is hand-rolled (`core/message.rs:265-267`).

## Rejected leads and severity corrections

1. **F1, sub-claim "with `key_generation` set, the engine regenerates a key by itself".** The code path exists (`eng/session_runtime.rs:292-300,1424-1427`), but it never runs in shipping builds: the Swift wrapper always passes `generate_key = 0` (`swift/MTProtoRustEngine/RustNetworkSession.swift:191`), so `ffi:628` never sets `key_generation`. In production MTContext does all key creation after `handleMissingKey`. In fact the engine's DH handshake code (AUTHKEY area) does not run in the shipping app at all, which matters to the group auditing AUTHKEY. The rest of F1 stands as M1, with a concrete duplicate-execution scenario.
2. **F4, "at session start".** NET cannot exploit this. `Session::new` draws a fresh random session_id (`core/session/mod.rs:348`) with an empty duplicate window (`:378`), so no recorded packet passes the session_id check (`:1197`) before the first genuine packet synchronizes the clock; only SRV picks the initial clock, as in tdlib. The exploitable part is mid-session resets combined with TooOld replays (L1). Its root cause, which the map does not name, is that Replay-mode packets reach `observe_server_time`; tdlib avoids this.
3. **F8 severity Low → Info.** Tokens are 31-bit values derived from SHA-256 over key-dependent data. They are kept per connection only (cleared at `core/session/mod.rs:772,827`, at most 256 at `:2403`), so forging one targeted token needs about 2^31 injected frames (≈ 8 GiB) inside one connection. tdlib handles quick acks the same way (`Session.cpp:788` sets `is_acknowledged_`).
4. **F2 severity Low → Info.** It needs the auth key (SRV); NET cannot produce msg_ids at all, and tdlib behaves identically.
5. **F9 severity Low → Info.** The effect is UI-only. Forging a head that maps to a pending query without the key has 2^-64 odds; replaying a genuine head only re-reports progress of the real answer.

Confirmed without change: F3 (as L2), F5 (as L3), F6, F7, F15, F17, F18 (as L6), F20, F21, F22, F23. For these areas the engine-map's "NET: no panics" claim holds: I re-checked every slice and arithmetic step in `codec.rs` (`decode`, `classify`, `trim_padded_payload`), `message.rs` `decrypt_message`, `progress_target`, `dedupe.rs`, `read_bounded`, and `update_progress` (progress is reset per decoded frame, `eng/session_runtime.rs:1186`).
