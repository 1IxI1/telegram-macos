Attackers: **NET** on-path without the key (no proxy secret ⇒ obfuscation keys are in the clear header, so NET can read, inject and replay frames, even into a later connection of the same session); **SRV** key holder (Telegram DC); **CDN** key holder of a CDN DC (untrusted per docs); **HOST** Swift caller bug.

Key facts that frame every row:
- In the app the engine never creates keys: `setup.generate_key = 0` (`RNS:191`); `.authKeyCreated` is logged and dropped (`RNS:573-574`). DH, temp-key creation and `auth.bindTempAuthKey` are MtProtoKit's (audited separately).
- `useTempAuthKeys` is hard-coded `true` (`NET:510`); the host's selector is `ephemeralMain`/`ephemeralMedia` for main and workers, `persistent` only for CDN (`RNS:1299-1304`).
- `RustEngineRuntime.shared` is a process-lifetime singleton; `mt_engine_destroy` is never called (`RER:131-139`, grep: no caller).
- CDN downloads only happen with the Rust engine: FetchV2 sets `cdn_supported` only when `fastDownloads = network.engineKind == .rust` (`FV2:439`, `FV2:927`); V1 always sends `flags: 0` (`MPF:352`).

## Confirmed findings (sorted by severity)

### B-1 (Medium) `AUTH_KEY_DUPLICATED` is never acted on: the client keeps using an invalidated key in a retry storm
- **Where:** `core/rpc/mod.rs:696-699` (406 ⇒ `SoftAuthReset` + surface only); `RustNetworkSession.swift:508-512` and `Network.swift:465-467` ⇒ `Account.swift:1365-1367` (log upload, rate-limited 30 s); `Network.swift:1356-1359` (`retryRequest`, no error filter, linear 0.2 s→5 s); `AccountStateManager.swift:874-878,1462-1466` (getDifference "skip").
- **Scenario (host/integration bug; matches the owner's live observation on dc2 main):** once the server answers 406 `AUTH_KEY_DUPLICATED`, it has invalidated the key (docs `/api/errors#406`). Every TelegramCore caller re-issues its request on the same key, so ~30 independent pollers at the 5 s cap produce ~340 failures/min; `help.getConfig` is one of them (`ManagedConfigurationUpdates.swift:11`). Nothing drops the key, rebinds, or logs out.
- **Triggers present in the code:** (a) `SwitchingNetworkEngine.switchEngine` resumes the replacement main session while the previous one keeps its live connection for `drainTimeout = 5.0` s (`SwitchingNetworkEngine.swift:136-175,177-196`; `Network.swift:1115`), both on the same `ephemeralMain` temp key: two TCP connections sending requests in parallel, exactly what the docs and the engine's own integration note R3 forbid; (b) the main session and home-DC `upload`/`background` workers share one temp key (`RustNetworkSession.swift:1299-1304`, `Network.swift:1145-1151`), contrary to DOC-PFS-11.
- **tdlib:** no special case in this checkout either, but its callers back off exponentially (`UpdatesManager.cpp:1302-1316`), so it never storms.
- **Fix:**
  1. Engine (`rpc.rs` `handle_error`): for `406 AUTH_KEY_DUPLICATED` on a non-CDN session, quarantine the current `auth_key_id`: park this and every later request (`rejected_key = Some(key)`, backoff 1, 2, 4 … 60 s, as `park_for_temporary_key` at `rpc.rs:714-732`), make `is_ready` false while the session key equals the quarantined id, close the connection, and emit a new `RpcEvent::AuthKeyDuplicated { key_id }` at most once per key.
  2. Host: on that event for an ephemeral selector call `handleMissingKey(rejectedKeyId: installedKeyId, engineStillHoldsKey: true)` (drop the temp key, rebind through MtProtoKit) with its own exponential backoff. If the new key also gets 406 within 10 minutes, or the bind fails with 401/`ENCRYPTED_MESSAGE_INVALID`, call `networkSessionAuthorizationRequired()`, which is the docs-mandated re-login.
  3. TelegramCore: do not retry 406 `AUTH_KEY_DUPLICATED` in `retryRequest`/`retryRequestIfNotFrozen`, and back off the getDifference "skip" path exponentially.
  4. Root causes: in `switchEngine`, pause the previous session's connection (`previous.setPaused(true)`) before `replacement.setPaused(isPaused)` and move its pending requests at once; give each concurrent home-DC session its own temp key, or keep to one main-DC connection unless `tmp_sessions > 1`.

### B-2 (Medium) A hostile CDN can silently truncate any CDN-served file (FetchV2)
- **Where:** `FetchV2.swift:881-882` (an empty `cdnFile` returns `verifyPartHashData: nil`, so it is committed unverified at `:1008`); `:535-569` (the hash loop only covers the returned bytes, so a short answer that ends on a 128 KiB boundary verifies); `:1268-1282` (`knownSize = min(known, lowerBound + count)` plus `.resourceSizeUpdated`).
- **Scenario (CDN, which the docs call untrusted):** while a user downloads a document or video that the master redirected to a CDN, the CDN answers one `getCdnFile` with 0 bytes, or with only the first 128 KiB of a 256 KiB request. The file is stored and shown as complete at the truncated size. Substitution is still blocked. The path is only live under the Rust engine (`FetchV2.swift:439,927`). tdlib fails the download in this case (`PartsManager.cpp:389-394`).
- **Fix:** for `.cdn` parts, treat `bytes.size == 0` or `data.count < requestedLength` as a CDN failure (count it toward `cdnVerificationFailures`, so it falls back to the master). The only exception is when `fetchRange.lowerBound + data.count` equals the master-authenticated end of file: the known media size, or the end of the last `FileHash` range. Never lower `knownSize` from CDN data.

### B-3 (Medium) A hostile CDN can set the app-wide clock
- **Where:** `core/session/mod.rs:1212-1213,1308-1318` (any odd msg_id raises the clock before the window check); `core/rpc/mod.rs:559-561` (CDN not filtered); `session_runtime.rs:1377-1386`; `RustNetworkSession.swift:541-542` (`context.setGlobalTimeDifference` for every role).
- **Scenario (CDN):** the CDN sends one packet with a msg_id at now+N years. The shared `MTContext` global time jumps forward and stays there, because the main session re-reports only when its own value moves by 1 s or more. Effects:
  - `ManagedAutoremoveMessageOperations.swift:44-79` deletes every message with an autoremove timer locally;
  - outgoing messages get future timestamps (`EnqueueMessage.swift:593,913`);
  - MtProtoKit's next bind uses `expires_at = globalTime + 24 h` (`MTBindKeyMessageService.m:56`);
  - DoH config timestamps are checked against the wrong time (`MTBackupAddressSignals.m:169,319`);
  - new sessions start from the poisoned offset (`RustNetworkSession.swift:193`).
- **Parity:** tdlib also lets any session raise the global time (`Global.cpp:189-196`); MtProtoKit only does it on bad_msg 16/17.
- **Fix:** in the host, apply `.timeDifferenceUpdated` only when `isMain` (at minimum `!isCdn`). In the engine, optionally cap forward jumps for `SessionRole::Cdn` and do not emit `TimeDifferenceUpdated` for CDN sessions.

### B-4 (Medium) An unauthenticated `-404` re-keys every session that shares the temp key and re-executes in-flight queries (engine-map F1 plus host amplification)
- **Where:** `session_runtime.rs:1313-1321,1698-1700` (all requests, including in-flight ones, requeued for a new key and session); `RustNetworkSession.swift:522-527,826-872` (drops the key from the shared context); `:938-959` (other sessions on the same selector pause); `session_runtime.rs:243-251` and `core/session/mod.rs:862-904` (on the new key every such session resets and requeues its in-flight queries).
- **Scenario (NET, with no proxy secret):** one injected 4-byte `-404` frame on any main, upload or background connection to the home DC forces a new DH and bind for all of them. Every query that had already reached the server is sent again in a new session, where the server cannot dedupe it, so a call without a `random_id` runs twice (e.g. `channels.createChannel`). Natural temp-key expiry does the same thing (B-7). tdlib re-keys only the affected session.
- **Fix:**
  1. Give each session its own temp key, so the blast radius is one session.
  2. On a key loss, requeue only never-sent (`Pending`) requests. Fail in-flight ones (`Sent`/`Unknown` with `may_have_arrived`) to the caller with a retryable error such as `500 AUTH_KEY_LOST_IN_FLIGHT`, and let TelegramCore's idempotency rules decide.
  3. Apply the same rule to `install_key` with a different key id.

### B-5 (Low) CDN DCs receive the full `initConnection`
- **Where:** `RustNetworkSession.swift:192`; `core/rpc/mod.rs:443-448`; `core/rpc/wrap.rs:39-91`; `Network.swift:480-507`.
- **Scenario (CDN):** the CDN operator learns the device model, OS version, app version, language pack, the user's MTProxy address and the app JSON `params`. This is parity with MtProtoKit, but it is new exposure in practice because CDN downloads only happen under Rust.
- **Fix:** for `SessionRole::Cdn`, build tdlib's anonymous header: `"n/a"`/`"n/a"`, empty lang pack and code, no proxy, no params (`MtprotoHeader.cpp:37-76`). Alternatively the host passes an anonymized `MTEnvironment` when `isCdn`.

### B-6 (Low) A CDN can stall a download indefinitely
- **Where:** `core/rpc/mod.rs:583-586` parks `401 AUTH_KEY_PERM_EMPTY` for every role. `RustNetworkSession.swift:519-521` then regenerates the CDN key on each report (at most once per 30 s, `rpc.rs:25-27,714-723`). FetchV2 has no per-part timeout.
- **Scenario (CDN):** the CDN answers every `getCdnFile` with that error, or never answers. The download never fails over to the master DC, and the client runs a DH with the CDN every 30 s. This violates DOC-CDN-11.
- **Fix:** for `SessionRole::Cdn`, surface `500` and drop the CDN key, as tdlib does (`Session.cpp:948-958`). Add a per-part CDN deadline in FetchV2 that triggers `fallBackToMaster`.

### B-7 (Low) Temp keys are never rotated before expiry
- **Where:** engine F19 (no use of `expires_at` after `session_runtime.rs:1197`); no expiry tracking in the host; MtProtoKit purges only at context load (`MTContext.m:476-490`).
- **Scenario:** in a long-running macOS process the main temp key dies server-side about every 24 h. Recovery goes through the `-404` path with the B-4 consequences, plus an outage. tdlib rotates 60 min before expiry.
- **Fix:** the host schedules regeneration and bind at `validUntilTimestamp - 3600` and installs the new key only once the session is idle (or hands queries over without requeuing in-flight ones).

### B-8 (Low, malicious master DC only) CDN redirect parameters are not validated
- **Where:** `FetchV2.swift:884-889,947-957`; `MultipartFetch.swift:372-386,434-440`.
- **Scenario (SRV):** an `encryption_iv` shorter than 4 bytes causes an out-of-bounds `memcpy`; an empty one crashes on a force-unwrap. Key and IV sizes are never checked.
- **Fix:** require a 32-byte key and a 16-byte IV, as tdlib does (`FileDownloader.cpp:95-96`); otherwise fail the redirect and download from the master.

### B-9 (Info) `destroy_auth_key` is never sent after logout
- **Where:** `AccountManager.swift:507-526` (DOC-SVC-20, TD-PFS-14). Parity with MtProtoKit.

### B-10 (Info) Deviations from tdlib in tolerance thresholds; none is a security issue
- Dropped-answer budget is 8 MiB per 10 s versus tdlib's 256 KiB cumulative (`core/session/mod.rs:43,50-51,1656-1669`).
- `rpc_answer_*` arriving as the result of a live, non-cancelled query leaves that query pending (`core/session/mod.rs:1686`).
- Trailing bytes after service messages are ignored (`core/tl/mtproto.rs:468-546`).
- `new_session_created` salt is adopted (`core/session/mod.rs:1732-1736`).
- Container ordering and seqno are not checked, and `msgs_all_info` is not correlated with a request (`core/session/mod.rs:1462-1464,1512-1525`).

### B-11 (Info) FFI and secrets hygiene issues, unreachable in the app today
- F10 race (`lib.rs:188-207`).
- F11 Debug derives on secret-bearing types (`eng/types.rs:10-15,60-76,122-135`; `core/rpc/wrap.rs:15-34`) and `PartialEq` on `AuthKey`.
- F12 unzeroized copies.
- F13 undocumented header contract.
- F14 NaN only matters if injected after sync, and the host never does that.

## Rejected leads

- **bad_msg_notification / bad_server_salt for messages never sent, used for clock or salt poisoning:** rejected. The engine requires `was_sent` and excludes both from Replay mode; duplicates are ack-only (`core/session/mod.rs:970-978,1431,1579,1498-1510`). This is stricter than tdlib.
- **Unsolicited `future_salts`:** rejected; `req_msg_id` must be one of the last 8 requests (`core/session/mod.rs:1473-1478`).
- **`rpc_result` delivered to the wrong query, or a cancelled query's answer causing trouble:** rejected.
  - msg_ids are monotonic and unique per session; resend unmaps the old id; cancel unmaps and sends `rpc_drop_answer`.
  - Engine request ids are globally unique, and the host maps them per session.
  - Late answers are only counted toward the dropped-answer budget (B-10).
- **CDN answers accepted for other DCs:** rejected. Each `Session` has its own `by_msg_id`; there is one mailbox and one `pendingById` per session; hashes and reuploads go to the master.
- **Updates from CDN or unencrypted connections:** rejected; filtered in the engine (`core/rpc/mod.rs:543-547`), by the absence of host sinks (`Network.swift:1137-1139`), and by the handshake-only plain path.
- **Server-sent `destroy_auth_key_ok` wiping the key:** rejected. It only produces an event if the client requested destruction, and the host has no handler for that event.
- **API queries sent on an unbound temp key:** rejected. The host always passes `allowUnboundEphemeralKeys: false`, and MtProtoKit publishes ephemeral keys only after bind; `AUTH_KEY_PERM_EMPTY` is parked and never surfaced. A future change that installs keys from another source would remove this protection, because the engine has no gate of its own.
- **Spoofed or replayed 401 forcing logout:** rejected. A 401 arrives inside an authenticated `rpc_result`; a replayed old one cannot match a live msg_id, and Replay mode only acts on live state.
- **`AUTH_KEY_PERM_EMPTY` reaching logout:** rejected (`core/rpc/mod.rs:583-586` runs before the 401 branch).
- **`msg_resend_req` making the client upload a query forever:** rejected; at most 8 resends per query (`core/session/mod.rs:56,1557-1563`). The counter can overflow (F23), but only after about 32 GB of input.
- **Use-after-destroy, double destroy, or callbacks after `mt_engine_destroy`:** unreachable. The engine is never destroyed, handles are never reused, and the mailbox is removed before `mt_session_destroy`.
- **F14 NaN wedging sessions in the app:** rejected. The host never passes NaN and never calls `mt_session_set_time_difference`; NaN at creation self-heals.
- **F10 key zeroization race in the app:** rejected; the engine never generates keys in the app and is never destroyed.
- **NET transient clock rollback via F5 (withheld answer replayed after more than 300 s) propagating to `MTContext`:** downgraded to Info. The main session's next genuine packet re-syncs the clock and re-reports the change, which is larger than 1 s, so the context is corrected within one RTT. The MSG area (group A) owns F4/F5.
- **NET-triggered `AUTH_KEY_DUPLICATED` by replaying captured packets over a second TCP connection:** not confirmable client-side, because it depends on whether the server counts replayed (deduplicated) messages as parallel use. Listed only so the server team can check it; B-1's fix bounds the damage either way.
- **Engine-level retry loop on 406:** rejected. The engine surfaces 406 once per request (`core/rpc/mod.rs:696-699`), so the storm in B-1 comes from TelegramCore callers.
